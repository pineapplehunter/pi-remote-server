# Pi Remote WebSocket protocol v1 (v0.1 milestone)

This is the server implementation contract. No production server is included.

## Transport and authentication

- One outbound connection per running Pi extension runtime.
- Default URL: `wss://pi.s.ihavenojob.work/agent/ws` (editable).
- Authentication is the HTTP upgrade header `Authorization: Bearer <token>`.
- Never use token query parameters or credential-bearing redirects.
- TLS is required except for `ws://` loopback development.
- JSON text frames only. No subprotocol is required.
- Agent accepts incoming frames up to 1 MiB (1,048,576 bytes).
- Incoming `text` is limited to 100 KiB (102,400 bytes), measured as decoded UTF-8.
- Oversized frames may close the connection at the WebSocket layer; other invalid messages return an error.

Every agent → server message includes `version: 1`, `type`, and `session_id`.
Session IDs are Pi's own SessionManager IDs, not generated by this extension.
Treat IDs as opaque strings. Error envelopes use the **current** session ID.

## Agent → server

The examples below show the complete shapes. `s1` is only an example ID.

```json
{"version":1,"type":"session.register","session_id":"s1","host_id":"laptop","cwd":"/work/project","name":null,"pid":12345}
{"version":1,"type":"session.updated","session_id":"s1","name":"Debug tests"}
{"version":1,"type":"session.unregister","session_id":"s1","reason":"quit"}
{"version":1,"type":"session.status","session_id":"s1","status":"working"}
{"version":1,"type":"session.status","session_id":"s1","status":"idle"}
{"version":1,"type":"message.completed","session_id":"s1","role":"user","content":"Run the tests"}
{"version":1,"type":"message.delta","session_id":"s1","delta":"The problem "}
{"version":1,"type":"message.completed","session_id":"s1","role":"assistant","content":"The problem is resolved."}
{"version":1,"type":"activity.started","session_id":"s1","activity":{"kind":"tool","tool_call_id":"call1","tool":"bash","args":{"command":"npm test"}}}
{"version":1,"type":"activity.completed","session_id":"s1","activity":{"kind":"tool","tool_call_id":"call1","tool":"bash","is_error":false}}
{"version":1,"type":"error","session_id":"s1","code":"wrong_session","message":"Message targets a different active session."}
```

### Lifecycle semantics

- The first application messages after every connection are `session.register`, then current `session.status`.
- Register on session start/reload/replacement, and again after reconnection. Registration is idempotent, not creation of a new session.
- Name changes produce `session.updated`; clearing the name sends `name: null`.
- Unregister reasons: `quit`, `reload`, `new`, `resume`, `fork`.
- Unregister is best effort. A server must also handle disconnected clients; no unregister delivery guarantee exists.
- Session replacement/reload closes the old runtime's connection and starts a fresh one.
- `working` starts with `agent_start`; `idle` means `agent_settled`, after automatic retries/compaction/queued continuations.
- Socket connectivity is independent of agent status.
- If two Pi processes resume the same Pi session ID, they may share an ID. Track registrations per connection (and host/pid); do not assume a session ID uniquely identifies a live process.

### Chat and activity semantics

- Only finalized user/assistant text is forwarded. Unsupported content blocks are omitted.
- Concatenate `message.delta` into the current assistant draft. Deltas are incremental, not cumulative; thinking is not forwarded.
- Each assistant `message.completed` is authoritative: replace the draft with `content`, then clear the draft for the next assistant message. Assistant tool-call-only messages can have empty textual content.
- Do not append both the draft and completed text as separate messages.
- No message IDs, history replay, application acknowledgments, or delivery guarantees in v1.
- Disconnects may lose events or part of a streamed draft. Final completions received after reconnect remain authoritative. Registration starts a fresh transient draft/activity view.
- Tool calls may execute in parallel: correlate activity by `tool_call_id`, not event adjacency.
- Tool results and tool updates are never forwarded.
- Tool arguments larger than 16 KiB, unserializable arguments, or arguments containing the configured bearer token are replaced with `args: {}` and `args_omitted: true` inside `activity`.
- Messages/stream text containing the configured bearer token are redacted; secrets other than this token are not automatically detected. This is a trusted remote conversation feed.

## Server → agent

Only this message type is accepted:

```json
{"version":1,"type":"message.send","session_id":"s1","text":"Say hello from the remote client"}
```

Validate exact numeric `version: 1`, supported `type`, non-empty string `session_id`, matching active session, and non-whitespace string `text` within the limit. Unknown object properties are ignored. Whitespace around otherwise valid text is preserved.

Idle input is injected through Pi's normal user-message API. Busy input is queued as `followUp`, never used to steer/interrupt. During automatic retry/compaction gaps, a bounded session-local input queue (32 messages / 1 MiB) defers delivery until Pi streams again or settles; queue overflow returns `injection_failed`. Configuration changes/session replacement discard those transient pending inputs. Slash-command/template expansion is disabled: input is literal conversation text. The eventual `message.completed` for the user input is its normal conversation echo, not an acceptance acknowledgment.

Errors: `invalid_json`, `invalid_message`, `unsupported_version`, `unsupported_type`, `text_too_large`, `wrong_session`, `injection_failed` (synchronous API failure only). Error wording is human-readable and not stable; use `code`. Pi handles asynchronous agent errors itself. Binary frames return `invalid_message`. Frame size violations may close instead of returning an error.

Malformed traffic must not stop Pi. No error payload echoes incoming text.

## Reconnect and server responsibilities

Client retries after approximately 1s, 2s, 5s, 10s, then 30s maximum; successful opens reset the schedule. No persistent or offline event queue exists. Live socket buffering is bounded and a persistently slow socket is replaced rather than blocking Pi.

The server should authenticate the upgrade, route only to the intended live registration, discard transient state after disconnect, and send only the above `message.send` frames. No automatic resend/deduplication is specified: retrying a request can submit it twice. A WebSocket connection is not proof that Pi accepted an application message.
